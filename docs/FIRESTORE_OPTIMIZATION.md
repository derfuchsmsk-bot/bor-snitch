# Отчет по оптимизации Firestore и архитектуры БД

## 1. Текущее состояние
В данный момент проект находится в стадии гибридной архитектуры. Мы успешно внедрили слой репозиториев (`src/repositories/`), но старый модуль `src/services/db.py` продолжает существовать как "прослойка" (wrapper), выполняя две функции:
1.  **Обратная совместимость:** Проксирует вызовы к новым репозиториям, выбрасывая `DeprecationWarning`.
2.  **Хранилище сложной логики:** Содержит бизнес-логику, которую сложно просто перенести в CRUD-репозитории (например, транзакционное сохранение итогов дня, проверка AFK).

Это создает технический долг, так как логика размазана между сервисами, `db.py` и репозиториями.

## 2. Выявленные проблемы

### A. `src/services/db.py` как "God Object"
Файл `db.py` нарушает принцип единой ответственности. Он знает слишком много:
- Как парсить сообщения Telegram (`log_message`).
- Как начислять штрафы за AFK (`check_afk_users`).
- Как проводить амнистию (`apply_weekly_amnesty`).
- Как управлять транзакциями обновления статистики (`save_daily_results`).

**Риск:** Любое изменение в логике начисления очков требует правки "файла базы данных", что нелогично.

### B. Утечка бизнес-логики в слой данных
Методы вроде `check_afk_users` и `apply_weekly_amnesty` содержат "магические числа" (конфигурацию) и правила игры. Им не место в слое доступа к данным.
*   *Пример:* `db.py` решает, что AFK — это 2 дня, и штраф — 50 очков. Это должна решать `GameService` или `AnalysisService`.

### C. Неоптимальные операции чтения
Метод `check_afk_users` использует `stream()` для получения *всех* пользователей чата, а затем фильтрует их в Python.
*   **Проблема:** При росте количества пользователей в базе это станет медленным и дорогим (Read Operations).
*   **Решение:** Перенести фильтрацию на уровень запроса Firestore (`where('last_active_date', '<', cutoff_date)`).

### D. Сложные транзакции
Метод `save_daily_results` выполняет массивную транзакцию: читает глобальный документ, читает N документов пользователей, вычисляет новые ранги, пишет обратно.
*   **Риск:** Конфликты транзакций при одновременной активности (хотя блокировка `daily_analysis` в `AnalysisService` частично это решает).

## 3. План оптимизации (Roadmap)

### Фаза 1: Разделение ответственности (Refactoring)
Цель: Очистить `db.py` от бизнес-логики, превратив его в пустой файл или удалив вовсе.

1.  **Перенос `log_message`:**
    *   Логику парсинга сообщения и определения "текст или стикер" перенести в `ChatService`.
    *   В репозиторий `MessageRepository` передавать уже готовый словарь данных (DTO).
2.  **Перенос `check_afk_users`:**
    *   Логику ("кто виноват") перенести в `AnalysisService`.
    *   В `UserRepository` добавить метод `get_inactive_users(days_threshold)`, который выполняет оптимизированный запрос.
3.  **Перенос `apply_weekly_amnesty`:**
    *   Логику перенести в `GameService`.
    *   В `UserRepository` добавить метод `batch_update_scores(updates_dict)`.
4.  **Перенос `save_daily_results`:**
    *   Это самый сложный метод. Логику расчета новых рангов и очков нужно вынести в `GameService`.
    *   Репозиторий должен предоставлять атомарный метод `commit_daily_stats(updates)`.

### Фаза 2: Оптимизация запросов Firestore

#### 1. Индексация для AFK
**Текущий запрос:** `collection("user_stats").stream()` (Full Scan)
**Оптимизированный запрос:**
```python
cutoff_date = now - timedelta(days=2)
query = stats_ref.where(filter=FieldFilter("last_active_date", "<", cutoff_date))
```
*Требуется создание композитного индекса в Firestore, если мы будем фильтровать и по `season_id`.*

#### 2. Оптимизация `get_logs_for_time_range`
Сейчас мы просто фильтруем по `timestamp`.
*   Убедиться, что существует индекс `chats/{chat_id}/messages` -> `timestamp (ASC)`.

### Фаза 3: Полный переход на Repositories
1.  Заменить все импорты `from src.services.db import db` в `handlers.py`, `analysis_service.py` и др. на инъекцию соответствующих репозиториев.
2.  Удалить `src/services/db.py`.

## 4. Предлагаемая структура (Target Architecture)

| Компонент | Ответственность | Пример методов |
| :--- | :--- | :--- |
| **Handlers** | Прием команд, вызов сервисов | `cmd_start`, `on_message` |
| **ChatService** | Логика общения, реакций, парсинг | `process_incoming_message`, `should_snitch` |
| **GameService** | Правила игры, подсчет очков, ранги | `calculate_new_rank`, `get_afk_penalty_amount` |
| **AnalysisService** | Оркестрация анализа (AI + DB) | `perform_daily_analysis` |
| **UserRepository** | **ТОЛЬКО** I/O операций с юзерами | `get_inactive_users`, `update_stats_transaction` |
| **MessageRepository**| **ТОЛЬКО** I/O сообщений | `save_log`, `get_range` |
